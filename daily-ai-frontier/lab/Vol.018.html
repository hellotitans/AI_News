今日概念 · TODAY'S CONCEPT

KV Cache:AI 接下一句话,
为什么比第一句便宜

今天的日报被两条「便宜」刷屏:DeepSeek 的毛利率超过 Anthropic 与 OpenAI,OpenAI 把 API 价格永久砍半。可模型明明越聊越长、算的东西越来越多,怎么反而越用越便宜?拆到推理引擎的底层,答案指向同一本「账本」——KV Cache。它不产生任何智能,却决定了每一次调用的电费。今天把它拆开看懂。

概念卡 · IN ONE SENTENCE

KV Cache(键值缓存)指大模型在生成每一个字时,把前文算出的「键(Key)」与「值(Value)」中间结果保存下来;生成后面的字时直接取用这些旧账,只新算当前这一个字。它把「每写一个字都要把前文重读重算一遍」的重复劳动,变成一次计算、处处复用——这正是长对话与长文档处理的边际成本不断摊薄的底层机关。

一个类比 超市收银台的小票。收银员扫到第 50 件商品时,绝不会把前 49 件重新扫一遍——它们的品名、单价、数量都记在小票上,只需处理眼前这一件,再往小票上添一行。对话越长,小票越长:记小票本身要占地方(显存),但比起每扫一件就全场重扫一遍,记账便宜得多。危险也藏在小票里——它一直在变长,台面(显存)迟早被占满,这正是长上下文「贵在存、不在算」的原因。
No.1

原理拆解

How It Works

三层递进:这本账怎么记;它和「老老实实重算」的根本区别在哪;以及为什么省钱与爆显存,来自同一个设计。

01

第一层:逐字生成的「记账」动作

大模型是一个字一个字往外蹦的:每生成一个新字,注意力机制都要「回看」前文所有字,才能决定下一个字写什么。每个字在前文里会留下两样中间结果——键(Key,「我在哪、像什么」的索引)与值(Value,「我携带的信息」)。没有缓存时,生成第 1000 个字要把前 999 个字的 K/V 全部重算一遍,浪费惊人;有了 KV Cache,旧账已存好,新字只算自己的一份 K/V,再去查旧账即可。生成因此从「每步重算全文」的平方级,降为「每步只读旧账」的线性级。

02

第二层:与「重算一切」的根本区别——瓶颈从算力搬到显存

老办法是「每来一个字就从头读题」,新办法是「边读边记账」。这一换,把推理的瓶颈从计算量(FLOPs)搬到了显存与带宽:账本要一直躺在显存里,而且越攒越厚。这解释了推理时代 GPU 的真正痛点——常常不是算不动,而是装不下、读不快。于是你看到各家拼命做「账本瘦身」:多查询注意力(MQA/GQA)让多个字共用一份账、KV 量化把账本压缩存档、DeepSeek 提出的 MLA 更是把账本压到极致。省下的全是显存,拼的全是记账功夫。

03

第三层:省钱与爆显存,为何同源

缓存越大,生成越快越省——这是它的力量;但缓存随对话长度线性增长,一个用户聊到一万字,显存里就躺着一万字的账,成千上万用户并发时,显存会先于算力见底——这是它的危险。力量与危险来自同一个设计:把计算结果留在身边复用。由此衍生出整套工程学:预填充与解码分离(先集中记账、再快速吐字)、前缀缓存(大家共用同一段「开头账单」)、以及决定「谁的账先被扔出去」的置换策略。读懂这一点,你就读懂了推理厂商报价单背后的成本结构。

No.3

常见误解

Common Myths

三个最容易搞错的地方——聊天的 credibility 就从这里来。

✗ 误解一

「对话越长,后面每个字生成起来和开头一样费力,所以长对话应该按长度平方计费才对。」

✓ 实际上

每个新字的计算都因缓存而轻——真正随长度线性增长的是显存占用(账本变厚),而不是每个字的计算量。长对话变贵,贵在「存」越来越厚的账,不在「算」越来越慢;这就是为什么长上下文按存储与带宽计价,而非按计算量计价。

✗ 误解二

「缓存就是把问题的答案存起来,下次有人问同样的问题,直接把旧答案抄一遍。」

✓ 实际上

它缓存的是注意力计算的中间状态(键与值),不是答案本身——省掉的是「重读前文」的功夫,「思考新内容」一步不少。前缀缓存可以让很多人共用同一段「开头账单」,但生成仍要逐字进行。它是「免于重读」,不是「免于思考」。

✗ 误解三

「KV Cache 是免费的午餐,开了就一定更快、更省、更划算。」

✓ 实际上

缓存吃显存:并发一高,显存先于算力见底,系统反而要「扔账」、换出、重算,得不偿失。工程上要在保留多少、压缩多少(量化)、复用多少(前缀共享)之间做取舍。免费的只有第一眼的直觉——真正的账,永远记在显存上。

Q1

不许用「缓存」「键」「值」这三个词,用你自己的话讲清:为什么 AI 聊到第五十句时,第五十一句不用把前面五十句从头「读」一遍?它靠什么做到又快又省?代价又是什么?提示:想想超市收银小票或会议纪要——第一次记下来,后面只查不重算;再想想这些记录本身放在哪里、会不会越堆越厚。

Q2

一次对话从一百句拉长到一千句,每个新字的计算量、以及显存占用,分别大致怎么变?为什么说长上下文「贵在存、不在算」?这和 GPU 厂商拼命宣传显存容量有什么关系?提示:每步计算只跟「新字+回看」有关,但那本账要一直躺在显存里;想想小票的长度 vs 每扫一件商品的工时,分别对应什么资源。

Q3

你是推理服务负责人,老板发现用户提的问题八成都以同样一段公司介绍开头。你会怎么设计来省钱?省下的是什么资源?又会遇到什么新问题?提示:大家共用同一段「开头账单」,可以只记一份;但并发一高,显存里同时躺着成千上万份不同的「后半段」,谁先被扔出去、扔出去之后要不要重算?

  1. 一句话版本:KV Cache = 把已算过的注意力中间结果(键与值)存下来,新 token 只算自己的一份再去查旧账——把逐字生成从「每步重算全文」的平方级,降为「每步只读旧账」的线性级。长对话越聊越「便宜」的边际成本曲线,机关全在这里。
  2. 关键转移:瓶颈从算力(FLOPs)转移到显存与带宽。GQA/MQA、KV 量化、前缀缓存、MLA(DeepSeek 提出)都是「账本瘦身」术——省的是显存,拼的是记账功夫。长上下文贵,贵在存,不在算。
  3. 代价与危险:缓存随上下文线性增长、吃显存;高并发下显存先于算力见底,于是有预填充/解码分离、前缀缓存(共用开头账单)、置换与重算策略。同一份设计,既是省钱的钱袋,也是显存的炸弹。
  4. 加分项(聊资):下次看到「API 降价」「长上下文白菜价」「毛利率超越 OpenAI」,先问一句——是算力便宜了,还是账记得更聪明了?能分清这两者,你就比大多数人更接近推理经济的真相。
